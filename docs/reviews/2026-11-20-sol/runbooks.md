# Runbooks, actions, approvals and LLM review

## Verdict

The design can display all four runbook forms and handle an unseen format with a manual import path. The executable path needs a durable worker queue, a shared approval state machine and a config-defined HTTP action to meet the brief.
This is a design review. Throughput and crash recovery remain unmeasured.

## Scalability — findings

- **High — §6.2 and §8 leave execution placement undefined.** Slow targets, retries and waits can stall the API or streaming workers. Return 202 after persisting an action intent. A separate action role claims due rows with short Postgres leases, executes async outside the transaction, and persists results with lease fencing. Bound concurrency, response size, timeouts and attempts. Scale workers independently and cap their DB pool. Persist delayed work with a due time.
- **High — §6.3 leaves replay and crash semantics undefined.** Simultaneous approvals, API retries and worker crashes can repeat a side effect. Atomically consume the pending approval, append audit and insert a unique execution intent. Freeze alert instance, runbook version, step ID, action version and validated rendered params at request time. Send one stable execution ID to idempotent targets across attempts. A timeout or crash after dispatch to a non-idempotent target yields an uncertain result for manual reconciliation. Queue claims give at-least-once processing, with effect deduplication dependent on the target.
- **High — §6.4 can close the wrong occurrence.** A source's recovery event may fail the firing predicate, and stale timers or old action results can race a new match. Route typed recovery signals through a recovery predicate and the same rule/correlation key and partition. Check source ordering where available. Atomically close only the intended alert generation, rechecking the last-match generation for quiet timers and action-driven closes. Give quiet timers to the partition owner so it can process earlier buffered matches before firing. Emit the close audit and update in the same transaction.
- **Medium — §6.1 and §9 need a bounded attachment path.** Compile templates and match predicates once per config revision. Index candidates by team and schema or rule, attach and render a bounded snapshot on alert creation, and reuse it across channels. Duplicates update the counter. Audit only transitions with actor, channel, alert/step/version, execution ID, timestamp and redacted outcome. Keep secrets and raw event bodies out of audit.
- **Medium — 20k/s at UI p99 <250 ms is plausible only for a bounded workload and requires measurement.** Postgres writes and channel fanout grow with newly created alerts, while repeated matches can be cheap. At 1% new alerts, 20k events/s means 200 new alerts/s before fanout. Report new-alert ratio, runbook sizes and fanout. Measure ingest-to-browser SSE for newly created alerts, report duplicate counter freshness separately, and repeat under slow action targets while tracking queue age and p99. §3 is right to keep LLM requests outside the event path. Deduplicate proposal jobs per unknown shape or incident revision, rate-limit them and bound sample retention.

## Flexibility — findings

- **High — §6.1 covers four inputs but arbitrary formats need a manual path.** Use explicit format selection and preview. Preserve original source and expose an editable checklist for unrecognized documents. YAML adapter maps Appendix B's flat action parameters and equality map into typed params and the shared predicate representation. Markdown list items become manual steps, with approval phrases displayed as hints. Render Markdown without raw HTML or unsafe URLs. Store wiki links with optional user-supplied labels and skip server-side fetch. Preserve free text verbatim and optionally propose manual steps or references to registered actions. New structured grammars need an adapter, while a judge can attach and edit their document immediately.
- **High — §6.1 leaves selection and step semantics ambiguous.** Prefer explicit rule binding, then team-scoped eligible candidates by explicit priority and stable ID. Retain an immutable runbook version and stable step IDs. Separate manual text, conditions shown as guidance, and executable actions. For Appendix B, count recorded terminal retry failures for the current alert instance and expose escalation after two failures. Arbitrary natural-language conditions cannot safely drive execution. Render only designated template fields from the pinned event context with strict missing-field behavior and contextual escaping. Disable invalid actions with a visible reason.
- **High — §6.2 requires Rust for every new verb.** Register an HTTP action plus named config entries containing a fixed target alias, method, typed parameters, request template, credential reference, timeout and risk. Use configured mock origins for the demo, encode path/query values, serialize JSON fields, disable redirects and keep event values out of the origin, credentials and headers used for authorization. Validate at publication and before execution. Risk in the registry sets a minimum approval requirement. New HTTP integrations become config-only and custom protocols still use the trait. Record the action definition version.
- **High — §6.3 needs one approval policy across channels.** The UI user picker demonstrates actors and needs a real identity boundary before live integrations. Scope pending requests to eligible approvers and show the rendered request with secrets redacted. SMS challenges are expiring, sender-bound, attempt-limited and accepted through an authenticated gateway callback. Email signatures bind the approval request, decision, approver, nonce and expiry. GET shows a confirmation screen and POST consumes the request, so scanners cannot approve. Revalidate the current alert state before claiming execution. Record rejection, expiration and cancellation as audit transitions.
- **High — §3, §4.2 and §6.5 leave the proposal trust boundary underspecified.** Give the model no tools or execution credentials. Send bounded synthetic or explicitly allowlisted and redacted content, including free text and audit notes, which can carry PII even after field masking. Treat inputs and outputs as inert data. Accept typed proposals only after server validation and authorized human review with a preview. Mapping proposals select existing paths and approved transforms and must pass a sample preview. Generated steps can reference registered actions and inherit their risk policy. Post-incident changes show a redacted diff against a base revision and require re-review if the revision changed. Publishing a proposal changes configuration. Execution still uses the ordinary run and approval endpoints. §4.2 already provides a good fallback through raw-field matching and manual path selection.

## Proposed spec edits

- **§6.1, replace the format/model and selection contract.** “Import YAML, Markdown, a link or plain text. Preserve the source and allow manual checklist editing for unfamiliar formats. Only validated structured steps can bind a registered action. Pin runbook revision and step IDs to each alert. Explicit rule binding wins, then team-scoped matches by configured priority and stable ID.”
- **§6.2, replace the extension and execution contract.** “Register named HTTP actions by configuration with fixed target aliases, typed templates and a minimum approval policy. Other protocols implement Action. A separate action role leases persisted intents and runs them with bounded concurrency and timeouts. Idempotent targets receive the same execution ID on retry. Uncertain non-idempotent outcomes require reconciliation.”
- **§6.3 and §8, replace approval execution semantics.** “Approve a frozen action request through the same atomic transition for UI, authenticated sender-bound SMS and signed email confirmation POST. Consume the expiring request, append redacted audit and enqueue the execution intent in one transaction. Accepted runs return 202 with an execution ID.”
- **§6.4 and §4.2, replace the resolution contract.** “Map recovery to a typed boolean and correlate it through a recovery predicate and the same incident key. Quiet timers and resolving action completions close only the current incident generation after a transactional state check.”
- **§3 LLM row and §6.5, replace the control contract.** “Optional rate-limited workers submit bounded redacted inputs to the configured provider without tools. Typed outputs remain drafts until validated and explicitly published by an authorized user against the reviewed revision. Action risk and approval policy apply to published steps.”
- **§9, add a scenario.** “Run ingest under stalled action-worker targets. Report alert creation ratio, fanout, UI p99, duplicate counter freshness, action queue age and recovery after the target returns.”
