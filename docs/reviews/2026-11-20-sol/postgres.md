# Postgres and sqlx review

## Verdict

Keep Postgres 16 as the authority for alerts, checkpoints, deadlines and delivery intents. The design needs explicit fencing, alert-generation rules and retry semantics before it can claim exact counts and durable delivery.
The laptop target is plausible for duplicate-heavy or low-match traffic and unverified for high-cardinality fanout. The demo primary is a write bottleneck candidate and a single point of failure.

## Scalability — findings

- **High · Checkpoint and replay (§2, §5).** An atomic snapshot alone allows a revoked consumer to commit after a replacement takes ownership. Key checkpoints by pipeline/topic/partition. On assignment acquire the DB row, advance the ownership epoch, restore state and seek to the stored **next offset**. Lock and validate epoch plus expected checkpoint before every flush, including timer-only flushes. Commit dirty state, deadlines, alert/audit/outbox mutations and the consumed prefix together. After an ambiguous commit, reload durable state and seek before reapplying any delta. If the stored offset is outside retention, stop and report the gap. A replayed logical match at another Kafka offset can still double-count. Use transactional matcher output with read-committed consumers or stable match IDs deduped durably over the supported replay horizon.
- **High · Alert identity and timers (§2, §4.5, §5, §6.4).** The open-only index lets an acknowledged incident spawn a second active row on recurrence. Use a partial unique index on non-null `(rule_id, fingerprint)` with the same literal predicate in the index and conflict target. An acked generation still counts and stops no-ack escalation. Specify the dedup window as sliding over last seen. On expiry, atomically retire the old dedup generation and create its successor. To preserve §6.4 resolution semantics, add a `dedup_active` flag and use `WHERE dedup_active AND status IN ('open','acked')`; the old incident can remain unresolved. If the product instead defines dedup expiry as resolution, the simpler status-only index suffices, with an explicit resolved reason and audit entry. Flush counts by generation ID and update count/last_seen/version only. Keep group and quiet deadlines with partition owners so quiet decisions include matches already buffered by that owner. Define ordering by processing time and persist deadline timestamps. Resolve signals, UI and runbook resolution use conditional transitions on the same alert row and invalidate pending timers. For shared escalation, claim indexed due rows with `SKIP LOCKED`, lock/recheck alert status and timer generation, then atomically record the transition, audit and intent. Use a consistent lock order for transactions touching both alerts and timers. [Postgres 16 partial indexes](https://www.postgresql.org/docs/16/indexes-partial.html) · [Postgres 16 locking clauses](https://www.postgresql.org/docs/16/sql-select.html)
- **High · Relay vs external delivery (§2, §5).** The unique key prevents duplicate intent rows only. A crash after a broker or provider ACK can repeat the effect. Claim bounded ready batches in a short transaction with `FOR UPDATE SKIP LOCKED`, setting a lease deadline and fresh token. Publish or dispatch outside the lock, then finalize conditionally on that token. Index ready and expired-lease work. Allocate the sequence under the alert lock. Persist a unique `(alert_id, recipient, channel, notify_seq)` with non-null components and propagate the same job ID downstream. Persist channel job acceptance before Kafka offset commit. The mock gateway deduplicates by job ID. SMTP is at-least-once. Rechecking state before dispatch reduces stale pages, with a race if ack/resolve arrives after that check. UI updates and normal lifecycle audit still flow. Commit alert-version updates to the same outbox when SSE needs a durable update signal.
- **High · Write budget and latency (§2, §9).** At 20k raw events/s, single-rule all-match traffic on one fingerprint can coalesce to one counter-row update per flush. With 1% new-alert yield and two jobs per alert, expect 200 alerts and 400 job inserts/s before samples, audit, SSE outbox and relay claim/completion updates. With 100% new-alert yield that becomes 20k alerts and 40k jobs/s before the same amplification. Multi-rule matches increase both rates. Use dirty-key, set-based writes in bounded batches, no per-event raw inserts, no per-duplicate audit. Keep first N sample refs plus one replaced latest ref per dirty alert. A one-second counter flush can itself add almost one second of update latency. Report first browser alert and existing-counter latency separately, or budget a shorter flush if both must meet 250 ms. Measure sustained client arrival latency, lag and drain, WAL bytes/s, transaction and pool waits, job claims, row contention and table churn for hot duplicate, mixed and unique/fanout runs. Use fixed hardware/Compose resources and publish match ratio, alert rate and jobs per alert. High-cardinality target remains unproven.
- **Medium · Availability (§1–2).** Workers scale across partitions and claim queues. Active writes still converge on one primary. During a PG outage pause durable processing and DB-dependent UI/send operations, bound buffers and let broker lag absorb work within retention. Resume from durable positions. Broker-acked HTTP ingest can continue while broker capacity remains. HA requires failover routing, tested reconnect/recovery and replication with a stated RPO. Async failover can lose acknowledged DB commits. HA improves availability and leaves write capacity on one primary.

## Flexibility — findings

- **Medium · Define config ownership (§3, §4.3–4.5).** Store versioned rules and preferences as validated JSONB under relational IDs/team/revision. YAML imports and API edits use the same validator and compare-and-set revision. Seed demo config once; explicit reload imports changes and reports conflicts. Commit config plus a ruleset revision and NOTIFY in one transaction. Subscribe before loading a consistent revision+rules snapshot, reconcile after reconnect and periodically, and swap only a successfully compiled revision. Use a dedicated listener connection. Keep the last good ruleset on invalid changes. Existing matches carry the revision and downstream decision inputs they need. Adding a schema, rule instance, preference or runbook is data within supported operators and formats. New rule operators, source protocols, channel providers, actions and parsers require code at their existing extension points, without a DB migration for each variant. [Postgres 16 LISTEN](https://www.postgresql.org/docs/16/sql-listen.html)
- **Medium · Keep historical records interpretable (§4.5, §6.3).** Store alert version, applied rule revision, team and effective rendered runbook or immutable runbook revision. Persist action execution ID and typed, versioned intent payloads. Keep relational status, references and timestamps, using JSONB for channel-specific payloads and audit details. Store sampled event ID plus broker locator if raw lookup is supported, and surface expiry after retention. Index the alert feed by team/recency and audit by alert/time. Use bounded retention for terminal outbox rows and explicit snapshot/window eviction. Keep SQLx and PG-specific locking/notification SQL at the persistence boundary. Changing databases would require reimplementing those semantics and testing recovery.

## Hackathon risk

- Use verified `sqlx = "=0.8.6"` with `default-features = false` and `postgres`, `runtime-tokio`, `migrate`, `json` (add `macros` if using compile-time macros). Start with typed runtime queries and checked-in migrations to avoid a build-time DB dependency. Budget a finite pool across replicas and reserve a connection for each listener. [SQLx 0.8.6 PgListener](https://docs.rs/sqlx/0.8.6/sqlx/postgres/struct.PgListener.html)
- Get fenced checkpoint + dedup + UI outbox running first. Exercise worker death before/after commit, stale-owner writes, relay death after broker ACK, ack/resolve racing a timer and listener reconnect. Then add the full recipient-keyed throttle and escalation stages. Compose HA and production-grade external delivery guarantees are out of demo scope. If time gets tight, use a single escalation step and keep durable intents. No implementation or measured throughput was available for this design review.

## Agreed with other reviewers

- Broker → postgres and postgres → broker (19:43) agree on epoch-fenced PG next-offset checkpoints with alert/window/outbox state in one transaction.
- Aggregation → postgres (19:44) agrees on fencing, acked counts, alert ID for flushes and owner-side quiet timer rechecks. Its proposal to preserve unresolved status after dedup expiry is reflected in the recommended separate dedup-active flag.
- Rules → postgres (19:44) agrees on versioned snapshots, reload reconciliation and one validation/CAS path for API and imports.
- Runbooks → postgres (19:43) and runbooks → delivery (19:44) agree on bound one-time approvals and atomic consume/audit/enqueue with a stable execution ID. Lease the action outside the approval transaction and reconcile ambiguous outcomes manually if the target has no idempotency contract.
- Delivery → all (19:43) agrees on short fenced claims, stable IDs, mock gateway dedupe and at-least-once SMTP. It also agrees with broker on recipient-keyed intents and atomic throttle/checkpoint plus job outbox, and with runtime on separate SSE and gateway latency metrics.

## Proposed spec edits

- **§1 Goals / §2 Single points of failure.** “Application workers scale horizontally within partition and queue limits. The demo uses one Postgres write primary and one broker. During a DB outage processing pauses and broker lag accumulates within configured retention. Production HA requires tested failover, primary routing and a documented replication RPO.”
- **§2 State and exactness.** “Fence each partition with a Postgres ownership epoch. On assignment restore committed state and seek to its stored next offset. Validate the epoch and prior checkpoint in every transaction that commits dirty window state, deadlines, alert mutations and outbox rows. Exclude duplicate logical matches separately from offset replay. Flush dirty counter rows in bounded batches. Measure first-alert and counter-update latency separately.”
- **§4.5 Alert (DB) / §5 Aggregate.** “At most one dedup-active alert per rule and fingerprint via a partial unique index covering dedup-active open and acked rows. Both statuses receive counts within the sliding window. Retire an expired generation before opening the next, preserving its lifecycle status. Persist alert/team/rule revision, alert version, deadline and outbox lease metadata, and immutable sampled broker locators subject to retention.”
- **§2 Outbox relay / §5 Deliver.** “Claim due rows with short fenced leases using SKIP LOCKED. Publish outside the transaction and conditionally finalize by lease token. Carry a stable per-intent job ID through delivery retries. Delivery is at-least-once; the mock gateway deduplicates by job ID. Workers recheck cancellation before dispatch.”
- **§3 DB / Config reload.** “API and YAML import write validated, revision-checked Postgres config. Commit a ruleset revision with its config and send NOTIFY as a reload hint. Subscribe before initial load, reconcile on reconnect and periodically, and atomically swap only successfully compiled snapshots.”
- **§6.3–6.4 Approvals / Resolution.** “Bind approvals to a pending execution, recipient and expiry. Atomically consume approval, append audit and enqueue a stable execution ID. Keep group and quiet deadlines with their partition owner. Escalation workers claim due timers with SKIP LOCKED, recheck the locked alert and timer generation, and commit transition, audit and intent together. Every resolution path conditionally closes the same generation.”
- **§9 Load testing.** “Report raw input, match and new-alert rates, job fanout, browser-received first-alert and counter latency separately, and mock gateway acceptance latency. Report backlog/drain and Postgres WAL and commit timing for hot duplicate, mixed and high-cardinality traffic.”
