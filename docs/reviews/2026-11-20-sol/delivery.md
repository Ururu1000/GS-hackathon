# Channels and delivery review

## Verdict

Keep the transactional outbox, channel isolation and simulator. Revise the delivery contract before implementation. Unique intent IDs prevent duplicate jobs, while SMTP still has an ambiguous acceptance window.
The architecture can support the outage demo after durable job handoff and recovery are specified. Laptop throughput and recovery remain unmeasured in this design review.

## Scalability — findings

- **High · §§2, 5.6.** A relay can crash after publishing but before marking the outbox row. Use short fenced `SKIP LOCKED` leases, publish outside the transaction, mark published after broker acknowledgement and retry expired claims with the same ID. Channel consumers upsert by job ID and commit only the contiguous offset after durable persistence. Keep retry scheduling in Postgres with an indexed due-time queue, bounded workers per provider and fenced completion. Sleeping on failed broker records blocks healthy jobs in the same partition.
- **High · §§2, 4.4–4.5.** The unique key protects job creation. A worker can crash after SMTP acceptance and before recording success. Preserve `(alert_id, recipient_id, channel, notify_seq)` across retries and use stable SMTP Message-ID for tracing. The fake gateway persists a unique job ID and receipt before replying, including across restarts. Resolve on-call/preferences once at dispatch planning and freeze routing for retries. The worker reads current alert eligibility immediately before every external attempt and records cancellation for ineligible jobs. An ack can still race an in-flight send. Apply per-kind eligibility to approval prompts, and always publish UI status changes.
- **High · §§2, 5.6, 9(c).** A 60-second outage can exhaust a fast retry budget. Use capped jittered backoff, classify transient/permanent/ambiguous errors, honor provider retry delays and bound each attempt. Open a breaker per provider endpoint after transient failures and allow one leased probe after cooldown. Leave deferred jobs pending without consuming attempts. Atomically record DLQ state and create one deterministic, configured fallback job, with a one-hop limit and a send-time eligibility check. Retain terminal failures for replay under the original job ID. An email fallback can cover a notification while its original SMS remains unsent, so report those outcomes separately.
- **Medium · §§2, 5.4, 9.** Recipient-wide throttling serializes a hot recipient, and Postgres WAL, job fanout and provider quotas limit delivery throughput. Route via durable recipient-keyed intents and checkpoint recipient and per-rule buckets with channel-job creation. Batch queue writes and report due-job age, provider acceptance rate and backlog drain rate. The single Postgres and broker instances in Compose are failure domains. Treat 20k/s as an ingest experiment with conditional UI p99. Measure match rate, unique alerts/s, duplicate ratio, jobs/alert, connected browsers and SSE updates/s. Browser-received SSE and mock acceptance need separate histograms. The 250 ms target is plausible only for a declared low-fanout workload until measured. Scheduled summaries and batching have their own latency.

## Flexibility — findings

- **Medium · §§3, 5.5–6.** Specify an async `Channel::send(job, rendered) -> Result<Receipt, SendError>` adapter registry keyed by channel/provider config. Use an immutable presentation/runbook snapshot and typed endpoint config. Keep rendering, retry policy and persistence in shared code. UI/email carry full filled-in steps, SMS carries a bounded title plus an absolute short link and optional approval challenge, and phone carries a brief TTS script. Use a configured public URL and escape content for its destination. UI delivery is persisted alert state plus a versioned update fanout and reconnect snapshot.
- **Medium · §3.** SES SMTP is endpoint/TLS/credentials/sender config plus provider setup. Twilio SMS/Voice needs a small outbound HTTP adapter that maps payloads, renders voice script with TwiML and returns provider IDs, plus signature-verified callbacks if replies or delivery status are enabled. Slack and Teams outbound need webhook adapters and destination config with provider-specific formatting. Interactive replies need a separate inbound adapter. Keep channel names extensible through the registry so routing, queues and retry logic stay unchanged. [SES SMTP](https://docs.aws.amazon.com/ses/latest/dg/send-email-smtp.html), [Twilio Voice](https://www.twilio.com/docs/voice/tutorials/how-to-make-outbound-phone-calls), [Twilio webhooks](https://www.twilio.com/docs/usage/webhooks), [Slack webhooks](https://api.slack.com/messaging/webhooks), [Teams Workflows](https://learn.microsoft.com/en-us/microsoftteams/platform/webhooks-and-connectors/how-to/add-incoming-webhook).
- **Medium · §§3, 5.5–6, 8.** Route simulator SMS replies through a trusted callback. Bind an expiring single-use challenge to the expected recipient, delivery and approval, then atomically consume it and enqueue the action. Use the same outbox for approval prompts. The phone simulator can display the script and simulate playback.

## Hackathon risk

Build one durable retry queue and simulator first. Run both SMS and phone through the same fake gateway with separate payloads. Use `lettre 0.11.23` with pooled Tokio SMTP and a configured timeout, and `reqwest 0.12.28` with a shared client and explicit request timeout. Mailpit's API supports inbox checks. Leave real providers and audio synthesis out of the demo. A durable leased provider cooldown is enough to demonstrate circuit breaking. [lettre transport](https://docs.rs/lettre/0.11.23/lettre/transport/smtp/struct.AsyncSmtpTransport.html), [reqwest](https://docs.rs/crate/reqwest/0.12.28), [Mailpit API](https://mailpit.axllent.org/docs/api-v1/).

## Proposed spec edits

- **§2, “No lost alerts” and “No duplicate pages”** — “Persist alert and outbox atomically. Relay with reclaimable fenced leases and stable IDs. Channel consumers durably upsert jobs before acknowledging broker records. External dispatch is at least once. The simulator deduplicates by job ID. Workers re-read eligibility immediately before each attempt. In-flight sends may complete after an ack.”
- **§3, Email and SMS/phone rows** — “Use pooled async lettre SMTP with Mailpit. SES SMTP uses endpoint, TLS, credentials and sender settings. Fake SMS/phone HTTP gateway persists each receipt by job ID and accepts trusted SMS replies.”
- **§5.5** — “Render committed presentation/runbook content per channel. UI/email get full steps, SMS gets a bounded title and absolute short link plus a challenge when needed, and phone gets a TTS script. Select the registered provider adapter from configuration.”
- **§5.6** — “Schedule retries in Postgres with capped jitter and a provider cooldown with one leased probe. Defer without consuming attempts during cooldown. Persist terminal failure and enqueue configured one-hop fallback atomically. Record cancellation, provider acceptance, terminal failure and replay by job ID.”
- **§9(c)** — “Send a known batch of unique eligible SMS jobs through ingest while SMS is unavailable for 60 s. Keep the transient retry horizon longer than the outage. Check UI/email progress independently. Restart the gateway and reconcile the expected job ID set with persisted simulator receipts and final job status. Assert every ID is accepted once, no IDs remain pending, none unexpectedly enter DLQ, and report drain time and attempt counts. Repeat with a response lost after durable gateway acceptance to test duplicate suppression. Use a separate forced-exhaustion case to verify exactly one DLQ entry and one fallback intent.”
