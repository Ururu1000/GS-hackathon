# Message broker review

## Verdict

Keep Redpanda and rdkafka. The Kafka partition model fits horizontal matching and stateful aggregation once the spec defines ownership, durable handoffs and replay.
The single-laptop target is plausible for small events with low alert fanout and batched writes. End-to-end performance and exact recovery remain unverified at the design stage.

## Scalability — findings

- **High · §2, §5 — Fence Postgres checkpoints.** A revoked worker can still have an in-flight write. On assignment, acquire a new epoch on the Postgres checkpoint row, restore window state and seek to its **next** offset before processing. Each transaction locks the row and verifies its epoch and expected starting checkpoint. Commit all effects for the processed partition prefix together, including timers, alert mutations and outbox rows. Synchronous first-alert writes must obey this boundary too. Stop dispatch on revoke and discard uncommitted local state. Disable Kafka auto-store and auto-commit for these consumers. The open-alert index cannot protect counters or replay after resolution.
- **High · §5 — Define the matcher replay boundary.** A crash after some match publishes but before the raw offset commit can replay those matches and inflate counts. Use batched Kafka consume–produce transactions with group offsets and downstream `read_committed`; abort on assignment loss. Stamp stable event ID, rule ID and rule version. At-least-once source retries can still produce multiple raw records with the same event ID. If exact business counts cover those retries, record logical match IDs transactionally with aggregation state and retain them for the supported redelivery horizon. Alternatively document counts per accepted raw record. A retry of an aborted matcher batch can evaluate a newer rule revision. Historical backtests need an explicitly selected revision.
- **High · §2, §5 — Put retries behind durable acceptance.** Use a PG intent outbox to publish `notifications` after resolving the recipient, then checkpoint throttle state and channel jobs atomically. The channel consumer commits only after idempotent durable job acceptance in PG. PG workers schedule retry timestamps with fenced leases, freeing Kafka partitions during provider outages. Publish `deliveries.dlq` and enqueue fallback from the durable terminal transition, keyed by stable job ID. A publish-ack/DB-mark crash can repeat Kafka records. Provider acceptance before a worker crash can repeat external sends unless the provider honors the job ID. Rechecking alert state before dispatch reduces stale sends while leaving a race with concurrent ack/resolve.
- **High · §2, §8 — Make SSE reconnect a state resync.** Per-replica groups correctly broadcast all updates, at broker/network cost proportional to replica count. Publish committed alert mutations via the outbox, key by alert ID and include version. Wait for group assignment and initialize the live subscription before serving SSE. On connection, subscribe and buffer before reading the team snapshot, then apply updates newer than each snapshot row; restart on buffer overflow or subscription interruption. A scalar partition offset cannot resume a multi-partition feed across replicas. Use ephemeral unique groups with bounded cleanup. The snapshot must also cover any delivery or approval state exposed by the feed.
- **Medium · §2 — Match keys to state ownership.** Unkeyed or event-ID keyed `events.raw` spreads stateless matching unless source ordering is a requirement. Use a canonical typed rule/fingerprint tuple for dedup and rule/group tuple for grouped rules, with dedup keys scoped within that group. Use stable user IDs on `notifications` and job IDs on channel/DLQ topics when send order is immaterial. Twenty-four fixed partitions allow up to 24 active workers per single-topic group; one fingerprint, group or user remains serial. Pin the partitioner and migrate state via a drained/versioned topic if the partition count or key changes. Report per-partition lag during the hot-key test.
- **Medium · §2, §5 — Bound queues and retention.** Bound producer queues and stage buffers by bytes and records; pause/resume Kafka partitions while continuing to poll. Keep ordered progress within each partition and commit only the processed prefix. Set time and disk budgets for every topic and alert on oldest unprocessed age relative to retention and on disk headroom. At 20k/s and 1 KiB per raw event, sustained raw payload alone is about 69 GiB/hour before compression, replication or downstream fanout. Check stored offsets against low/high watermarks and stop with a visible recovery error on gaps. Use an isolated preview/backtest consumer or explicit partition ranges so replay cannot page people or move production offsets. Keep pending channel jobs in PG through the supported outage window.
- **Medium · §9 — Measure stable throughput.** A 20k/s accepted ingress rate can coexist with growing downstream lag. Use open-loop load, publish accepted and processed rates, backlog and drain time, and record p50/p99 to actual browser receipt and gateway acceptance separately. Report payload size, rule count, match/unique-alert ratios, fanout, hardware and disk. A one-second counter flush or intentional group window cannot meet a 250 ms target for those outcomes. Measure immediate first-alert latency separately from duplicate visibility and group deadline lateness. Single-node compose has a broker and PG availability dependency, as §2 already states.

## Flexibility — findings

- **Strong · §5 — Adding a source instance or schema can be configuration-only.** Keep raw JSON and stable envelope metadata independent of broker wire types. Kafka configuration needs a source ID, bootstrap/auth, topics, group and explicit first-start offset policy. All replicas of one logical source share the group. A different source ID/group enables independent consumption. Keep upstream topic subscriptions distinct from the internal topics, especially when both use the demo Redpanda cluster.
- **Medium · §5 — The source trait needs a durable result.** A plain `run(tx)` is insufficient if sending only means local enqueue. Give adapters a bounded async publish interface returning the broker delivery result. Kafka commits the next contiguous upstream offset after durable publish and derives event identity from source ID plus topic/partition/offset. RabbitMQ uses bounded prefetch and manual ack after publish, derives identity from a producer message ID when available, and declares at-least-once behavior when that contract is absent. Preserve unacked messages for retry and route permanent decode errors to a separate ingest quarantine before acknowledging. A new protocol is a config variant, registered adapter and contract check; rule and normalization code stays reusable.
- **Medium · §3 — JetStream is a separate backend design.** Shared durable pull consumers offer load balancing and explicit acks. Kafka-style hash partition ownership, transactional match publish with source offsets, and per-partition Postgres seeks do not carry over. A JetStream implementation needs explicit subject shards, ownership/fencing, stream-sequence recovery and an independent delivery/replay contract. Keep client types at the adapter boundary. [NATS pull consumers](https://docs.nats.io/learn/jetstream/pull-consumers)

## Hackathon risk

- Pin `rdkafka 0.39.0` with `cmake-build`. At M0 verify native Compose build, advertised listeners from host and containers, broker-acknowledged produce, upstream offset commits and transactional matcher support on the pinned Redpanda image. The crate exists and exposes the needed APIs. [rdkafka installation and transactions](https://docs.rs/crate/rdkafka/0.39.0)
- Use webhook plus external Kafka ingest as the two source types. If RabbitMQ is needed later, `lapin 4.12.0` exists for AMQP 0-9-1. `async-nats 0.53.0` exists for JetStream. Crate availability is verified from docs.rs. Compose builds and interoperability remain unverified. [lapin](https://docs.rs/crate/lapin/4.12.0) · [async-nats](https://docs.rs/crate/async-nats/0.53.0)
- Prioritize crash tests at the matcher commit, stale aggregator epoch and channel acceptance boundaries. If matcher transactions miss the timebox, ship at-least-once matching with stable match IDs and transactional deduplication, or scope the demo claims to the checkpoint boundary.

## Proposed spec edits

- **§2, State and exactness.** “On assignment, the consumer acquires a new Postgres epoch, restores partition state, and seeks to the stored next offset. Each commit verifies the epoch and atomically records the processed prefix, window state and deadlines, alert mutations and outbox rows. Retention gaps halt the affected consumer with an explicit error.”
- **§2, Horizontal scaling.** “Use 24 fixed partitions for events.raw, alerts.matches, and notifications. Key matches by rule/fingerprint, or by rule/group for grouped rules, with dedup scoped to the group. Resolve recipients into durable outbox intents and publish to notifications keyed by user ID. Checkpoint recipient and per-rule buckets with channel-job outbox writes. Each API replica uses a unique group to receive committed, versioned alert updates. On SSE connect or reconnect, buffer live updates before loading the team snapshot, then apply newer versions.”
- **§3, Broker row and §12.** “Redpanda via rdkafka 0.39.0 with cmake-build. M0 verifies Compose build and Kafka transactional produce. JetStream requires a separate ownership and replay design.”
- **§5, steps 1–2.** “Source adapters await durable events.raw publication before upstream ack. HTTP returns 202 after confirmation, 429 with Retry-After when local capacity is exhausted, and 503 on broker failure or ambiguous timeout. Kafka derives stable event IDs from source/topic/partition/offset. Matchers stamp rule version and commit output records and source offsets in a Kafka transaction. Aggregators consume read_committed.”
- **§5, step 6.** “Publish channel jobs from the outbox with stable job IDs. Consumers commit offsets after durable idempotent PG job acceptance. PG schedules retries and records terminal failure, DLQ publication intent and fallback. External sends are at least once where provider idempotency is unavailable.”
- **§8, SSE endpoint.** “SSE sends a team snapshot followed by versioned updates. Reconnect starts with a fresh snapshot.”
- **§9, metrics.** “Report accepted and processed throughput, lag and drain time, payload and fanout distributions, p50/p99 to browser receipt and mock gateway acceptance, and reconcile counts and job IDs after failure. Evaluate the 250 ms target on immediate UI alerts with stable backlog, and report group delay and duplicate counter visibility separately.”
