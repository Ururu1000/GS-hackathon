# Aggregation review

## Verdict

Partition-local windows without Redis are a reasonable fit for the demo. Group ownership, fenced recovery and recipient-side throttling need explicit contracts before implementation. The laptop throughput and latency targets remain unmeasured.

## Scalability — findings

- **High · Group ownership (§2, §5.3).** Different fingerprints for the same Pricing instrument can reach different partitions and each emit a digest. Key grouped matches by the rule and group tuple, keeping any nested dedup state on that owner. Use fixed five-minute UTC buckets over a stable match-ingress timestamp for Pricing. Persist bucket deadlines, flush due buckets even when idle, and finalize after a configured grace period. Count arrivals after finalization in a late-match metric and retain the raw event for inspection. Keep the partition count fixed during the demo. Increasing it remaps keys and requires draining or migrating live state.
- **High · Recovery (§2).** A crash after the first alert commits but before its checkpoint can replay its increment. A revoked worker can also overwrite a successor's snapshot or emit an overdue digest. Fence writes with a DB ownership epoch per topic/partition, acquired only on valid assignment, and verify it under row lock in every commit. Commit the next offset, dirty window state, alert mutations and durable publication intents together, including versioned UI updates with durable visibility, including first alerts and timer flushes. Stop revoked workers, discard stale buffered work, and seek to the PG offset on takeover. Surface a retention gap as an error. This gives exactly-once effects for consumed offsets. Matcher retries can still produce the same logical match at different offsets, so use stable match IDs with bounded persisted replay deduplication if exact logical event counts are promised.
- **High · Alert identity (§2, §5.3).** An open-only unique index neither protects acked incidents nor distinguishes a new window from an existing incident that is still open. Define dedup as a sliding inactivity window with a persisted generation ID. Acked alerts keep accumulating in the current window without reopening or paging. Resolved alerts end the generation. Subsequent matches after expiry can start a new generation, even if the old alert is still awaiting resolution. Let the partition owner evaluate quiet timers after earlier buffered matches. Lock the alert and compare the timer's expected generation and last-seen value before resolving. Route typed source-resolution signals to the same incident key.
- **High · Throttle durability and locality (§2, §4.3, §5.3–4).** A pure global per-rule bucket would split across fingerprint or recipient partitions. The illustrated cap is per (rule, recipient), which fits alongside the recipient-wide cap on the recipient owner. Route first, deduplicate recipients reached by several routes, and debit both enabled buckets atomically once per recipient intent before expanding into channels. Persist the bucket state, intent replay guard, pending suppression count/deadline, offset and channel outbox together. Emit the digest when quota returns, even with no newer traffic. Keep the original alert available in the UI and bound digest metadata by keeping a count and samples. A strict rule-wide cap, if needed later, requires rule-keyed ownership or a transactional counter.
- **Medium · Hot keys and benchmark (§2, §5.3, §9).** A 500/s fingerprint is plausible if it means 500 local increments and roughly one coalesced count write and SSE update per second. The owner still handles all its traffic and can delay neighboring keys. Batch dirty keys per partition and expire inactive state. A one-second flush can add almost a second to visible count updates. Send first alerts promptly and report first-alert p99, counter freshness and group delivery lag after deadline separately. Sweep match rate, distinct keys, recipient fanout and skew at 20k raw events/s. Include a sustained 500/s fingerprint, a high-cardinality run and a mid-run owner kill, reporting lag, drain time, alert counts, PG commit rate and losses. High unique-match or fanout rates can saturate PG and the relay even if raw ingest passes.

## Flexibility — findings

- **High · Configurable identity (§4.3).** A fallback based on presentation fields makes cosmetic edits change identity and can silently group unrelated events with missing keys. Use validated field paths over mapped or raw data, canonical typed tuples and explicit missing-field behavior with a diagnostic. A new source or schema can reuse aggregation through mapping and rule config. Version identity/window changes and let existing groups drain under their original config. Rule kinds needing cross-rule or cross-key correlation require a new ownership model and code.
- **High · Route and preference precedence (§4.4, §5.4).** As written, rule channels, team defaults and personal preferences can conflict. Define explicit user, team and on-call targets. Expand team/on-call targets, choose the first matching user preference, then team defaults, then the rule's fallback channels. Preserve a rule's explicit channel restriction where specified. For Anna, evaluate the UTC dispatch-planning instant in Europe/London and use SMS during [08:00, 20:00), email otherwise. Pin this routing decision to the intent so retries do not change recipients during shift handover. Evaluate fresh on each escalation step. Team membership, rotation, channel selection and windows are config. A new channel needs its delivery adapter and render support. Actions and runbook formats can reuse the alert envelope and are owned by the extension points in §6.
- **High · Escalation (§4.4).** An unchecked timer can page an acked incident or enqueue the same step after restart. Store a durable step, due time and stable intent ID. Claim due rows using SKIP LOCKED and lock the alert row shared by ack/resolve. If open and still on the expected step, atomically enqueue the next distinct on-call recipient or lead and advance the step. Specify when the clock starts, what happens on suppressed/failed sends and how critical escalation interacts with throttles. Recheck open state at channel dispatch. A provider call already in flight can race with ack, and retry after ambiguous provider acceptance can repeat delivery unless the provider deduplicates the stable intent ID.

## Hackathon risk

- Prioritize one fenced recovery flow through aggregation before building the second stateful consumer. Use the same checkpoint mechanism for recipient buckets or, if time is tight, implement the same semantics with PG bucket rows and a durable pending-intent queue. Keep static weekly rotations, one bounded escalation chain and simple suppression digests. Prove crash recovery with counter, group deadline and outbox invariants plus an ack-versus-timer test. The no-Redis decision is sound under single-owner keys.
- [rdkafka 0.39.0](https://docs.rs/rdkafka/0.39.0/rdkafka/consumer/) exposes rebalance callbacks and seek. Spike revocation with an in-flight PG batch and verify that a successor resumes at the committed offset. [chrono-tz 0.10.4](https://docs.rs/chrono-tz/0.10.4/chrono_tz/) supplies IANA time zones. Check Anna at both boundaries and on either side of a DST change. Both APIs were checked on docs.rs. No executable implementation or load results were available.

## Agreed with other reviewers

- **Broker** (19:43 → aggregation, 19:44 reply) agreed on canonical group ownership and group-scoped dedup. The review proposes draining old identity versions or using a new rule ID.
- **Postgres** (19:43 → aggregation, 19:44 reply) confirmed the fenced next-offset transaction, counting while acked and checking the quiet timer under lock. The review favors releasing the active window pointer at expiry so UI lifecycle can continue independently.
- **Delivery** (19:43 → all) agreed on resolving recipients and preferences once, persisting the decision across retries, and committing both recipient bucket scopes with the channel outbox.
- **Rules** (19:43 and 19:44 → aggregation) agreed on typed key tuples, missing-key errors, stable event identity and separate config revision. Five-minute bucket alignment and lateness remain proposed details.
- **Runbooks and UI** (19:43 → aggregation and → all, 19:44 replies) agreed through the review board on typed incident resolution and quiet-timer guards, and on atomic alert versions, UI publication intents and visibility.

## Proposed spec edits

- **§2 diagram, Why this shape and Scalability details.** “Key matches by (rule, group tuple) when grouping is enabled and by (rule, dedup tuple) otherwise. Use 24 fixed partitions for the demo. On assignment, acquire a PostgreSQL ownership epoch and seek to its saved next offset. Fence all writes by that epoch. Commit dirty window state, the next offset, alert changes and publication intents in the same transaction. Stop work on revoke. Report broker retention gaps explicitly.”
- **§4.3 and §5 step 3.** “Use canonical typed keys from validated field paths and report missing keys explicitly. Preserve a window's original identity configuration across rule edits. Dedup increments the active generation, including while acked, until resolution or window expiry. Pricing emits one digest per instrument per nonempty five-minute UTC bucket, with persisted deadlines and a bounded late-arrival policy. Coalesce duplicate counter flushes.”
- **§4.4 and §5 step 4.** “Expand and deduplicate user, team and on-call destinations at dispatch planning time. Use the first matching personal preference, then team defaults, then rule fallbacks, subject to explicit channel restrictions. Evaluate local windows as start-inclusive and end-exclusive using the configured IANA zone. Publish stable recipient-keyed intents. Apply per-(rule, recipient) and recipient-wide limits before channel fanout. Commit bucket state, suppression deadlines, consumed offset and channel outbox jobs atomically. Flush suppression digests when quota returns.”
- **§4.4 Escalation.** “Start the critical escalation timer when its initial intent is durably queued. On expiry, lock and recheck the open alert and its expected step, then atomically advance the step and enqueue one intent for the next distinct on-call person or lead. Ack or resolve cancels pending steps. Give critical escalations an explicit throttle bypass and audit it. Persist the chosen recipient and channels across retries.”
- **§9.** “Report first-alert and UI latency, duplicate-counter freshness, and grouped-alert lag after the bucket deadline separately. State match rate, unique-key rate and delivery fanout for every reported raw ingest rate. Verify exact committed results during a sustained hot-key run and after a forced reassignment.”
